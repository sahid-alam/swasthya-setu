# Judge Q&A

One section per finished feature, generated by `/defend`. Every answer describes what
**exists** in the repo, not what is planned. Where something is mocked or synthetic, the
answer says so — an honest "that part is simulated, here is why that is the right call
at this stage" survives a follow-up question; a confident overclaim does not.

## IVR booking (PRD §M3, Tier 2) — 2026-08-21

### ⚠ Gaps — do not claim these

- **Nothing speaks.** The webhook returns the *text* a caller would hear; no TTS engine
  is wired. On a real line the provider speaks it, and the Bhashini voice work is the
  next two plan items. Demo it as "this is what the caller hears", never play a recording
  and imply we synthesised it.
- **Caller ID is the only identity.** Press 2 and the system reads back that number's
  upcoming appointments. Anyone who can spoof the caller ID hears them. A PIN or a
  one-time code would fix it; neither is built. Say this before a judge finds it.
- **The webhook is authenticated with our own staff JWT, not a provider signature.**
  Exotel would sign its requests and we would verify that; today the simulator logs in
  like every other simulator. That is a real deployment gap, not a demo shortcut.
- **A first-time caller cannot register by phone.** An unknown number is told to visit
  reception once. That is deliberate — we will not create patient identities from an
  unverified phone call — but it means the "farmer with a feature phone" must already be
  on the hospital's books.
- **`TELEPHONY_MOCK_MODE=true` and there is no `ivr_real.py`.** No Exotel account, no
  phone number, no live call has ever been placed. What is proven is the flow and the
  payload boundary, not the carrier link.

### Q&A

**1. How does a phone call actually reach your booking system?**
The provider POSTs one webhook per keypress to `POST /api/v1/channels/ivr/webhook` with
its own field names — `CallSid`, `From`, `Digits`. `adapters/ivr_mock.py` is the only
code in the repo that knows those names; it returns a `CallTurn`, and everything after
that speaks our domain. The reply is a `VoiceReplyOut` — what to say, how many digits to
collect, whether to hang up.

**2. Prove it. What do I run?**
`backend/.venv/bin/python simulators/ivr_call.py 9823872276 1 1 1` against a running
stack. It prints every prompt the caller hears and ends with a real appointment id;
`select channel from appointments where id = …` says `IVR`, and the confirmation is in
the outbox at `GET /api/v1/notifications` with `template: booked`. Run the same command
with `9868553803` and the whole call is in Hindi, because that patient's record says so —
she is never asked to choose a language.

**3. Is this a second booking system that will drift from the app?**
No. The flow calls `services/booking.py` — the same function the PWA, WhatsApp and the
staff desk call, including the capacity re-check under a `SELECT … FOR UPDATE` and the
no-show prediction. A channel decides how to *collect* the arguments; it never decides
the rules. `tests/test_ivr.py` asserts the appointment lands with `channel=IVR` and is
visible through the ordinary booking API.

**4. Why three options per menu when WhatsApp lists five?**
A WhatsApp user can scroll back; a caller cannot. Five spoken options exceed what a
person holds in their head, and by the time you read the fifth they have forgotten the
second. `IVR_MAX_OPTIONS = 3` is the whole difference, and the same constant caps the
"hear my appointments" list.

**5. Every input is a single digit. How do you know what "1" means?**
State is read before intent. At the menu, `1` starts booking; while a department list is
pending, `1` is department one. That ordering is the same lesson the WhatsApp flow was
built around, and it has its own test — reading intent first sends a caller round the
menu forever.

**6. What happens when the caller says nothing, or presses the wrong key?**
The session stores the last *clean* prompt and replays it behind a short apology; the
state does not move. That matters because advancing on a bad press leaves the caller
indexing a list they can no longer hear. Review caught the first version storing the
apology too, so a second wrong press stacked it — fixed, with a test that presses wrong
twice and asserts both replies are identical.

**7. What if the line drops mid-call, or two people call at once?**
Session state lives in Redis keyed by the call id with a five-minute TTL, so a dropped
call cleans itself up and a second worker can serve the next keypress. Concurrent calls
are independent by construction — the key is the call, not the number. Two callers
racing for the last seat: the second gets `BookingError` and hears "that time has just
been taken", because capacity is re-checked under the write, not at the time the option
was read out.

**8. What if the provider sends something malformed?**
It fails at the adapter with `AdapterError` and the webhook answers anyway: it says we
cannot identify the number and hangs up. A provider needs a 200 with something to play,
not a 500 — that is exactly what the adapter contract means by "degrade, never crash a
flow". This was a real 500 until review found it; there is now a test for the withheld
caller id.

**9. How much work is a real Exotel line?**
An `ivr_real.py` implementing `parse_call` for the live payload and rendering Exotel's
applet response, plus signature verification and credentials in `EXOTEL_SID` /
`EXOTEL_TOKEN` — which `.env.example` already reserves. `TELEPHONY_MOCK_MODE=false`
selects it. The flow, the prompts and the booking path do not change, which is the point
of putting the vendor behind an adapter.

**10. Why should a judge believe mock telephony proves anything?**
It proves the parts that are ours: the state machine, the language selection, the
booking, the receipt, the failure paths. It does not prove the carrier link, and we do
not claim it does. The alternative — a live number — would make the demo depend on
vendor uptime and venue signal, which is exactly the dependency Iron Rule 1 exists to
refuse.
